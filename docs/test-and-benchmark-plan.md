# 准确性测试与性能测试方案

目标有两个：

1. 让"这个库是对的"和"这个库是快的"两句话都有可复查的证据，而不是几次运行的印象。
2. 为探索更好的算法设计（例如用 TDD 尝试别的 double↔int128 转换思路）提供一个**候选实现擂台**：任何新实现一接入，就能自动得到"是否满足契约"和"相对现有实现快/慢多少"的结论。

## 实施状态（2026-11-10）

已实现：契约规格与 D1 输入检查（`check.hpp`）、参考实现自检、结构化穷举网格、8 种 frac bits 配置、性质测试、精度报告（`fixed128_accuracy_report`）、候选实现擂台（`experimental/candidates`）、性能测试（分档吞吐、延迟、场景、JSON 与对比脚本、汇编导出）、轨道漂移实验（`fixed128_orbit_drift`）、变异测试脚本、libFuzzer 目标、CI 中的 Debug / `/fp:strict` / `-march=x86-64-v3 -ffp-contract=fast` / sanitizer / fuzz 任务。
未实现：多微架构的实测对比（需要不同的机器）、云端以外的固定性能测试机器。

首轮结果：

- 契约在全部 8 种 frac bits、两个 backend、两种舍入方式下成立。
- **fixed128 → double 在 |x| < 2^96 个单位时 100% 正确舍入**；|x| ≥ 2^96 时约 1.7% 的结果朝 −∞ 偏 1 ULP（因此不是奇函数，属已知特性，未修改）。典型用法转换的是相近坐标之差，远小于 2^96 个单位（frac bits 36 时约 120 光年）。
- double → fixed128：四舍五入模式平均误差约 0；截断模式沿数值大小方向平均 −0.44 个单位（有偏）。
- 轨道漂移（木星系，Forest–Ruth 4，10 年，3 次扰动取中位数）：位置误差 double 约 1 km，Kahan 约 0.7 m，fixed128 约 0.9 m；整体平移 10²¹ m 后 double 完全失效（10¹⁰ m 级），Kahan 约 1.1 m，fixed128 结果与原点处逐位相同。fixed128 截断与四舍五入结果几乎相同（0.86 m 对 0.87 m），证实"double → fixed128 的舍入方式影响可忽略，主导误差的是 double 速度与引力计算"。leapfrog 100 年压力测试（平移 10²¹ m）：fixed128 43 m，Kahan 66 m，能量误差增长指数 fixed128 约 0.6（接近无偏随机游走的 0.5）。
- 由此对 D3 的结论：**目前没有证据需要为 fixed128 → double 的正确舍入付出开销**。
- 变异测试：15 个故意引入的错误（魔数差 1 ULP、借位丢失、舍入增量缺失、移位方向选择错误、输入检查边界等）全部被测试发现。首轮有一个"存活"的是等价变异（改的是库随后丢弃的借位输出），已换成真正改变结果的变异。
- CI 全部 9 个任务通过：MSVC（Release、Debug + `/fp:strict`）、GCC（含 `-march=x86-64-v3 -ffp-contract=fast`）、Clang（含 ASan + UBSan）、macOS ARM、Linux ARM、60 秒 libFuzzer 差分模糊测试。
- 输入检查抓到了原有测试自身的一个越界输入（fixed64 在 frac bits 52 时用了 1e6）；性能测试修正了一个测试代码伪影（循环内逐 lane 构造输入导致存储转发失败）。

## 第一部分：先把"契约"写成规格

测试只能检查写下来的东西。每个公开函数需要一行规格：输入定义域、输出、舍入方式、精度保证、定义域外的行为。

| 函数 | 定义域 | 结果 | 精度 |
|---|---|---|---|
| `double_to_fixed128_full` | \|v·2^f\| < 2^127（负数可到 −2^127） | 二进制补码 fixed128 | 精确；四舍五入（远离零）或截断 |
| `double_to_ufixed128_full` | 0 ≤ v·2^f < 2^128 | ufixed128 | 同上 |
| `fixed128_to_double` / `ufixed128_to_double` | 全部 128 位模式 | double | 与正确舍入值相差 ≤ 1 ULP |
| `double_to_int64_fast` / `double_to_uint64_fast` | (u)int64 范围 | 截断 | 精确 |
| `int64_to_double_fast_precise` / `uint64_…` | 全部 64 位模式 | double | 正确舍入（与硬件转换逐位相同） |
| `fixed128` 标量构造 / `operator double` | 同上 | 截断 / ≤ 1 ULP | — |
| 加减法（标量与 x4） | 全部 | 模 2^128 回绕 | 精确 |

**规格决定**（作者 2026-11-10 拍板）：

- **D1 定义域外（NaN、±Inf、超范围）**：Release 下**零运行时开销**，结果未定义。检查做成编译期开关 `FIXED128_CHECK_INPUTS`，未定义时默认值为 `!defined(NDEBUG)`（Debug 开、Release 关），违规时调用可覆盖的处理函数（默认 `assert` 式中止；测试里替换成抛异常，以便验证检查确实会触发）。和 `assert` 一样，同一程序里各翻译单元的开关应一致。
  测试：Debug 配置下验证每类非法输入都会触发检查、合法边界值不会误报；Release 配置下用反汇编或基准确认检查代码完全消失。
- **D2 −0.0 → 0**：已写进 README，并由边界用例覆盖。
- **D3 fixed128 → double 要不要花开销换正确舍入**：**先测量再决定**。依据是第二部分第 5 节的精度统计（重点看带符号误差的均值，即是否有偏）和第五部分的轨道漂移实验。只有当实验显示 ≤ 1 ULP 的误差在长期积分中造成可观的系统性漂移时，才考虑付出开销。

## 第二部分：准确性测试覆盖

### 1. 判定依据（oracle）本身也要被验证

所有测试都以 `tests/reference.hpp` 为准，所以它一旦错了，所有测试会"一致地错"。补强方法：

- 在 GCC/Clang 上用编译器自带的 `unsigned __int128` 再实现一遍关键运算（移位、取反、转 double），和参考实现做对拍测试。MSVC 没有这个类型，只在 CI 的 Linux 任务里跑。
- 对参考实现自身写几十个手算的已知答案（例如 `0x1p-37 → 1`（四舍五入）、`-0x1.8p-36 → -2` 等）。

### 2. 结构化穷举网格（替代"只靠随机"）

double 无法穷举，但它的结构可以：输入 = 符号 × 指数 × 尾数模式。

- **指数**：覆盖定义域内的**每一个**指数值（约 130–180 个），而不是随机抽样。
- **尾数模式**：全 0、全 1、只有最高位、只有最低位、每个单独的位、交替位、最高若干位全 1（容易触发进位），再加若干随机尾数。
- **舍入敏感点**：每个指数下的中点、中点 ±1 ULP、可表示值 ±1 ULP。
- **分段边界**：fixed128 被拆成 48+48+32 位三段、以及 64 位上下两半，每个边界 2^k 附近（k = 47, 48, 63, 64, 95, 96, 126, 127）的 ±1、±1 ULP。

规模约为 `2 符号 × 180 指数 × 约 150 尾数模式 ≈ 5 万` 个确定性输入，几毫秒跑完，每次都跑。

fixed128 → double 方向同理：按"最高有效位位置（0–127）× 低位模式（全 0 / 全 1 / 刚好在舍入位 / 舍入位加粘滞位 / 随机）"构造。

### 3. 配置矩阵

现在每种舍入方式 × backend 一个可执行文件，每个都测 frac bits 36 和 0（frac bits 是模板参数，见 ADR 0008）。frac bits 的取值会改变魔数常量，最容易藏 bug。建议把 `tests/test_helpers.hpp` 里的 `FIXED128_TEST_FRAC_BITS` 扩到：

| frac bits | 理由 |
|---|---|
| 0 | 纯整数 |
| 1 | 最小的非零值 |
| 36 | 默认值 |
| 52, 53 | 与 double 尾数宽度相等/相邻：`52 - f` 变为 0/负数 |
| 64 | 小数部分正好占满低半部分 |
| 100, 127 | 极端值：魔数 `2^(100-f)`、`2^(132-f)` 接近 1 |

每种都跑四舍五入和截断两种舍入；可执行文件数量不变。

### 4. 性质测试（metamorphic，不需要知道正确答案）

- **往返**：能被 fixed128 精确表示的 double，转过去再转回来必须完全相等。
- **单调性**：a ≤ b ⇒ conv(a) ≤ conv(b)（两个方向都要）。
- **对称性**：四舍五入模式下 conv(−x) = −conv(x)。
- **lane 独立性**：打乱 4 个 lane 的输入，输出按同样方式被打乱；某个 lane 的值不影响其他 lane。
- **x4 与标量一致**：每个 lane 的结果等于对应标量函数的结果（截断模式下标量构造也应逐位相同）。
- **加减与转换交换**：conv(a) − conv(b) 与 a − b 的精确值的关系（在可表示范围内应精确相等）。

### 5. 精度统计报告（不只是"通过/失败"）

fixed128 → double 的契约是 ≤ 1 ULP，但"有多少比例是正确舍入的"、"1 ULP 误差出现在哪类输入上"才是比较不同设计时真正有用的数字。加一个**报告模式**（命令行参数开启，默认不跑），对每个函数输出：

- 最大 ULP 误差、正确舍入的比例、按"最高位位置"分组的误差分布；
- **带符号误差的均值和分布**（结果偏大与偏小的比例）：均值显著偏离 0 说明舍入有偏，这是长期积分中误差累积的来源，D3 的决定主要看它；
- 产生误差的第一批输入样例。

double → fixed128 方向同样统计带符号误差：四舍五入模式应当无偏（只在恰好的中点上远离零），截断模式有固定的朝零偏差，报告中要能直接看到两者的差别。

这份报告也是将来判断"有没有更好的设计"时的核心证据之一。

### 6. 长时间随机测试与模糊测试

- **浸泡模式**：命令行参数 `--count`、`--seed` 控制随机用例数量和种子，本地或夜间任务跑 10^9 级别；失败时打印种子，可复现。
- **差分模糊测试**：用 libFuzzer（Clang）把字节流解释为输入，直接和参考实现对比。CI 上每次跑 1 分钟，本地可以跑几小时。

### 7. 编译器与编译选项矩阵

这个库的正确性依赖浮点运算顺序，所以编译选项本身就是测试维度：

- Debug / Release；`-O2` / `-O3`；MSVC 的 `/fp:precise` 和 `/fp:strict`。
- `-march=native` / `-march=x86-64-v3`：编译器可能自动使用 FMA 或 AVX-512 指令，改变代码生成。
- `-ffp-contract=fast`（GCC 默认就是这样）：确认不会被融合成 FMA 而改变结果。
- 在 Clang 上开 UBSan / ASan 跑一遍，主要检查标量代码里的移位和溢出。

### 8. 检验测试本身的强度（变异测试）

故意把实现改错，看测试能不能抓到。例如：把某个魔数改动 1 ULP、把 `cmpgt` 换成 `cmpeq`、删掉借位那一行、把 `blend` 掩码改一位。可以写一个脚本自动批量生成这些变体，也可以用 Mull 这类工具。**每个变体都必须让至少一个测试失败**，否则说明覆盖有漏洞。这是证明"测试有说服力"最直接的办法。

## 第三部分：性能测试方案

### 1. 每个数字要回答一个明确的问题

| 问题 | 测量方式 |
|---|---|
| 批量转换时每个值要多少周期？ | 吞吐：独立输入数组，按数据规模分档（见第 3 节） |
| 放在依赖链里会拖慢多少？ | 延迟：结果作为下一次的输入，测往返和单程 |
| 在真实用法里占多大比重？ | 场景测试：加载两组 fixed128 坐标 → 相减 → 转 double → 算距离（含 sqrt） |
| 比其他做法快多少？ | 与基线和候选实现对比（见第 4 节） |
| 理论上限是多少？ | uiCA / llvm-mca 静态分析的预测值，与实测对照 |

### 2. 测量方法

- **用周期而不是纳秒报告**，否则不同频率的机器之间无法比较。Linux 上 nanobench 能直接读硬件计数器（周期数、指令数、分支预测失败）。Windows 上读不到计数器，需要固定 CPU 频率后折算，或者主要在 Linux 上测。
- **控制噪声**：固定频率（关闭睿频或锁频）、绑定到一个核心、提高进程优先级、关闭后台程序；每项至少跑若干轮，报告中位数、最小值和离散度（nanobench 的 err%），err% 超过阈值的结果标红、不采信。
- **记录环境**：CPU 型号与微码、编译器版本与完整编译选项、提交哈希，随结果一起保存（nanobench 支持输出 JSON）。
- **核对汇编**：每个核心函数导出编译后的汇编，确认没有被编译器意外改写（例如外提常量、生成标量代码），并把指令数和注释里的数字对上。

### 3. 输入与数据规模

- **数据规模分档**：L1 内（8 KB）、L2 内（256 KB）、L3 内、超出 L3（主存带宽受限）。区分"转换算法本身的成本"和"访存成本"。
- **输入分布**：算法本身没有分支，理论上和数据无关，但需要验证：小数值、大数值、混合；特别要测会产生**非规格化数**（subnormal）的输入，部分 CPU 上非规格化浮点运算会触发微码辅助，可能慢上百倍。
- **内存布局**：SoA（现在的 x4 布局）与 AoS（xyz 结构体数组）之间的转换开销，也就是 `examples/xyz_lane_packing.cpp` 那类 shuffle 的成本。

### 4. 对比对象

- **基线**：标量硬件转换；标量 `fixed128`；GCC/Clang 上的 `(double)(unsigned __int128)`（编译器调用 libgcc 的 `__floattidf` 等函数）。
- **上限参照**：在支持 AVX-512DQ 的机器上，用原生 `vcvtqq2pd` 等指令拼出的版本，说明"如果有硬件支持能快多少"。
- **候选实现**：见第四部分。

### 5. 多种微架构

至少覆盖一代 Intel（如 Ice Lake / Alder Lake）和一代 AMD（Zen 3 / Zen 4）；手头没有的，用 uiCA（Intel）和 llvm-mca（可选 AMD 模型）做静态预测作为补充。`sllv`/`srlv`、`blendv` 这类指令在不同微架构上的延迟差别很大，结论可能因机器而异。

### 6. 回归跟踪

- 结果存为 JSON，写一个比较脚本：给出两次结果的差异和是否超过阈值。
- 云端 CI 的计时噪声太大，不适合做性能门禁；性能对比在本机或固定的自托管机器上跑。CI 只保证 benchmark 能编译、能运行一次（冒烟测试）。

## 第四部分：候选实现擂台（为探索新设计准备）

想回答"这个问题是不是真的没有更好的答案"，最有效的方式是让每个新想法都能被**同一套标准**快速裁决。

- **统一接口**：每个候选实现提供和现有函数相同的签名，放在独立目录（例如 `experimental/candidates/<名字>.hpp`），通过一个注册表列出。
- **契约测试模板化**：第二部分的所有测试写成对"任意满足签名的函数"生效的模板。新增候选只需注册，就自动跑完全部准确性测试和精度统计报告。
- **自动对比**：benchmark 遍历注册表，对每个候选输出吞吐、延迟、相对现有实现的倍数，以及 uiCA 预测。
- **TDD 流程**：先写（或复用）契约测试 → 新候选不通过（红）→ 实现直到通过（绿）→ 看性能对比决定去留。准确性测试是硬门槛，性能是比较项。
- **值得比较的指标**：指令数、关键路径延迟、吞吐、对端口的压力（uiCA 给出），以及 fixed128 → double 的精度（能否做到正确舍入）。

## 第五部分：轨道漂移实验（端到端的精度 + 性能测试）

单元测试只能证明"每次转换的误差在规格内"，回答不了"这些误差在几千万步积分后会不会累积成问题"。这个实验直接回答后者，同时给出性能数字，所以它既是精度测试也是性能测试。

### 先估算量级

frac bits = 36 时，一个定点单位是 2⁻³⁶ m ≈ 1.5×10⁻¹¹ m。以木卫一为例：轨道速度约 17 km/s，步长取 60 s 时每步位移约 10⁶ m。double 计算这个位移本身就有约 10⁻¹⁶ 的相对误差，也就是约 10⁻¹⁰ m，比定点舍入（最多半个单位，约 7×10⁻¹² m）**大一个多数量级**。所以可以预测：在这类场景里，double → fixed128 的舍入方式（四舍五入还是截断）对结果影响很小，主导误差的是 double 运算本身。fixed128 → double 的 1 ULP 误差进入的是引力计算，和 sqrt、除法自身 0.5 ULP 的误差同一量级。这个估算需要实验来证实或推翻。

### 实验设计

- **系统**：太阳 + 木星 + 四颗伽利略卫星（木卫一到木卫四），J2000 初始状态取自 `D:\Repos\Ephemeris`（himīśā 的星历积分器 [himisawww/Ephemeris](https://github.com/himisawww/Ephemeris)，作者同意自由使用）的 `initials/SolarSystem/SolarSystem_Initial.txt`，注明出处。坐标以太阳系质心为原点，木星离原点约 7.4×10¹¹ m，属于"大坐标、小相对距离"的典型场景。再做一组整体平移 10²¹ m（约 10 万光年）的版本，对应本库的目标尺度。
- **积分器**：固定步长的辛积分器。辛方法在没有舍入误差时，能量误差有界、不会长期漂移，所以任何长期漂移都只能来自舍入，信号最干净。
  - **主力：Forest–Ruth 4 阶**，与重力转向游戏里实际使用的积分器相同，结论直接适用于游戏。每步更新位置 4 次（系数约 0.68、−0.18、−0.18、0.68）、速度 3 次（约 1.35、−1.70、1.35），其中有"倒退"的子步。位置更新次数比 leapfrog 多，对位置表示的舍入是更严格的考验。
  - **压力测试：2 阶 leapfrog**，用更小的步长、更多的步数。舍入误差随步数累积（能量误差约按步数的 ½ 次方，相位误差约按 3/2 次方），步数越多越容易暴露问题。
  - **积分器阶数不会污染比较**：参考解 R 与各变体使用**同一个积分器、同一个步长**，只是算术精度不同，所以积分器自身的截断误差在"变体 − 参考"中相互抵消，剩下的只有舍入误差。阶数高低影响的是"在给定物理时长内走多少步"和"与游戏的贴近程度"，不影响结论的有效性。
  - 不用 Ephemeris 自带的 12 阶 Runge–Kutta：它不是辛方法，自身会有缓慢的能量漂移。与参考解的差值虽然不受影响，但"能量误差的增长指数"这个诊断要求积分器本身不漂移，否则无法分辨漂移来自舍入还是来自积分器。
- **对比的变体**（同一积分器、同一步长，只换位置的表示和更新方式）：

  | 变体 | 位置表示 |
  |---|---|
  | R 参考 | 全部用 double-double（约 106 位有效数字）计算，作为"真值" |
  | A | 纯 double |
  | B | double + Kahan 补偿求和更新位置（经典的低成本改进，是 fixed128 的直接竞争对手） |
  | C | fixed128，double → fixed128 截断 |
  | D | fixed128，double → fixed128 四舍五入 |
  | E | 将来如有：fixed128 → double 正确舍入的版本 |

- **指标**（按对数间隔的时间点记录，积分 10³–10⁴ 年）：
  - 每个天体相对参考解的位置误差，并分解为沿轨道方向（相位）和径向；
  - 总能量和角动量的相对误差。**看增长规律**：误差无偏时呈随机游走，约按 t^½ 增长（Brouwer 定律）；有偏时按 t¹ 线性增长。拟合出的指数就是"舍入是否有偏"的直接证据；
  - 每步耗时。
- **统计可靠性**：一次运行的舍入误差只是一个随机样本。对初始条件做若干组极小扰动（例如 1 ULP）重复运行，报告分布而不是单个数字。
- **呈现方式**：借鉴 SciML 的 work-precision diagram（三体问题那一页）：横轴是运行时间，纵轴是终点误差，每个变体是一个点或一条线（不同步长）。SciML 比较的是积分器，我们比较的是位置表示，但"误差对代价"的图正好同时回答精度和性能两个问题。
- **位置**：作为独立的实验程序放在 `validation/orbit_drift/`，不进 CTest（运行时间长）。CI 只跑一个 10 年的短版本作为冒烟测试，并检查"fixed128 变体的能量误差不劣于纯 double"。
