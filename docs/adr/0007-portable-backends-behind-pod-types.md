# Compile-time backends behind plain-struct lane types, bit-identical results

Supersedes the original AVX2-only decision (ADR 0001, since removed). The library is meant for a physics engine that must also run on Apple Silicon, which has no AVX2, so there are now two backends: AVX2 and portable scalar (4 plain C++ lanes, written to be auto-vectorizable). The backend is still chosen at compile time, never by runtime dispatch: `FIXED128_BACKEND_AVX2` / `FIXED128_BACKEND_SCALAR`, or automatically (AVX2 on x86-64, where a missing `-mavx2` stays a compile error instead of silently selecting the slow path; scalar everywhere else). CMake resolves `FIXED128_BACKEND=AUTO` once and propagates the explicit choice, because, like the other configuration macros, it must be the same in every translation unit.

The public 4-lane types (`double4`, `long4`, `ulong4`, `float4`) are plain `alignas(32)` structs with members `x, y, z, w` (lane 0 first) on every backend, so user code and data layouts do not depend on the backend; only `fx128::avx2::to_m256d` and friends expose intrinsics, and only with the AVX2 backend. Constructors taking 4 scalars now also take lane 0 first (previously `_mm256_set` order). We measured that crossing between these structs and registers is free once inlined (MSVC and Clang remove the stores and loads; the hot loops of every conversion compile to the same instructions as before). The one residual cost is that MSVC may set up a 32-byte-aligned stack frame (4 instructions per call, outside loops) in functions that use the structs.

The algorithms are written once, in a small set of vector primitives in `detail` (`detail/avx2/native.hpp`, `detail/scalar/native.hpp`). Each AVX2 primitive is exactly one intrinsic and takes the native `__m256i` / `__m256d` types: wrapping the registers in a struct made MSVC stop unrolling the calling loops (~10% slower). The scalar primitives emulate the exact semantics of those instructions (shift counts >= 64, byte-wise `blendv`), so both backends give bit-identical results, including the up-to-1-ULP error of fixed128 → double; a test hashes all results and compares with the value recorded from AVX2. Exact equality was chosen over a simpler `__int128` implementation so that simulations are deterministic across platforms. A NEON backend can be added by implementing the same primitives.
